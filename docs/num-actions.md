## 2. できないこと

実装を確認した限り、次の 3 つは**手段が存在しない**。

### 優先順位の変更 (順序変更)

`wh1 → wh2 → wh3` の並びが優先順位そのものだが、**並び替える UI が無い**。
`moveUp` / `moveDown` / ドラッグのいずれも未実装で、入れ替えるには
両方の語とかなを手で打ち直すしかない。

```mermaid
flowchart LR
  A["wh1: 鯉<br/>wh2: 恋"] -- "入れ替えたい" --> B["wh1: 恋<br/>wh2: 鯉"]
  A -. "手段が無い" .-> X["両方を手で打ち直す"]
  classDef gap fill:#fef2f2,stroke:#dc2626,color:#1f2937
  class X gap
```

### 番号の移動

「この語は 051 ではなく 052 だった」という移動手段が無い。
移動元で消して移動先で打ち直すことになり、そのとき
**`rep` / `ratings` / 画像はついてこない**。

### 番号単位の統合ビュー

1 つの番号について「語・かな・rankey・代表・評価・画像・確定状態」を
**まとめて見る画面が無い**。編集画面は語とかな、代表語コンソールは代表と評価、
画像コンソールは画像、と分かれている。

## 3. なぜ分散しているか

保存先が 3 つに割れていたため、面もそれに合わせて割れた。

```
シート          → 語・かな・タグ        → アプリ編集画面
word-rep.json   → 代表語・主観評価      → 代表語コンソール
word-images.json → 画像                → 画像コンソール
```

**Firestore 移行でこれは解消した。** `numbers/{num}` が全部持っている。

```json
{
  "num": "051",
  "hito": "...", "mono": "...", "gainen": "...",
  "slots": { "wh1": { "word": "鯉", "kana": "こい", "imageUrl": "..." } },
  "rep": { "picks": [...], "confirmed": true },
  "ratings": [{ "k": "こい", "w": "鯉", "v": 2 }],
  "derived": { "ptBySlot": {...}, "rankeyBySlot": {...} }
}
```

つまり **1 画面で全操作を提供する土台はできている**。
足りないのは操作の口を集約することだけ。

## 4. 決まったこと (次にやる 3 つ)

### A. 優先順位の変更を入れる

編集画面に並び替えを足す。`wh1 ⇄ wh2` の入れ替えが 1 操作で済むようにする。
語とかなを打ち直させない。

### B. 語単位の移動を入れる

番号ごと移すのではなく、**特定の語 1 つだけ**を別の番号へ移す。
`051 の wh2「恋」を 052 の wh1 へ` のような操作。

移動時に何が付いてくるかは、保存の形から自然に決まる:

| 付いてくるか     | 理由                                                                                           |
| ---------------- | ---------------------------------------------------------------------------------------------- |
| **かな** ○       | 語と一体。移動先で読みが変わることはない                                                       |
| **画像** ○       | `slots[].imageUrl` が語と同じ入れ物にある                                                      |
| **主観評価** ○   | `ratings` は `{k,w}` の**値**で保存されている。番号ではなく語に紐づく                          |
| **代表 (rep)** △ | 移動元で代表だった場合、移動先でも代表とは限らない。**移動元から外し、移動先では未設定にする** |

評価が付いてくるのは、スロット位置ではなく値で保存している設計の副産物。
「この語呂はアリか」という評価は語の性質なので、番号が変わっても有効。

### C. 番号単位の統合ビューを作る

1 つの番号の全情報を 1 画面に出す。`numbers/{num}` を読むだけで済む。

- 語・かな・rankey・pt (候補ごと)
- 代表 ①② と確定状態
- 主観評価
- 画像と確定状態 (`confirmedFor` とのズレ)

A と B の操作もここに置くのが自然。

## 5. テスト機能の要件

番号の編集とは別軸。「覚える」側の要件。

### D. タグを選んで出題範囲を絞る

`#tri` `#gen` `#進撃` のようなタグで出題範囲を決めたい。
「今日はこの作品の枠だけ」という詰め方ができる。

土台はある:

| 既にあるもの                 | 場所                                |
| ---------------------------- | ----------------------------------- |
| タグ一覧と番号の集計         | `app/lib/tags.js#collectNumberTags` |
| タグ選択 UI                  | `app/components/TagPanel.tsx`       |
| タグ → 正式名の辞書 (132 件) | `src/data/tags.json`                |

**足りないのは、選んだタグを出題側に渡す経路だけ。**
`TagPanel` は現状**閲覧用**で、選択がテストの出題範囲に反映されない。

出題側 (`KeypadQuiz` / `ChoiceQuiz` / `AssocTestTab` ほか) は
`questions` を props で受け取る形なので、**絞り込みは呼び出し側で完結する**。
出題コンポーネント自体は変えなくてよい。

### E. 答え合わせ中に重要度を切り替える

正解を見た瞬間が「この語呂はアリか」を判断できる最良のタイミング。
そこで手が止まらずに評価を付けられるようにしたい。

**評価の軸は既にある。** 代表語コンソールで使っている
主観評価 (`-1` / `0` / `+1` / `+2`) をそのまま使う。

- 保存先は `numbers/{num}.ratings`
- 値ではなく **`{k,w}` の組**で保存するので、候補が並び替わっても付いてくる
- `saveRating` が既に「`rep` と確定状態に触れない」部分更新になっている

答え合わせ画面から `saveRating` を呼ぶだけで、コンソールで付けた評価と
同じ場所に溜まる。**評価の入り口が 2 つに増えるだけで、データは 1 つ。**

> 未評価と `0` (普通) は別状態。答え合わせで何も押さなければ未評価のまま。

## 6. オプション (ラベル) の付与

語に付ける `-x` `-a` などの記号。実データで 8 種類が使われている。

| ラベル | 意味                                  | 機械判定 | rankey での対応                      |
| ------ | ------------------------------------- | -------- | ------------------------------------ |
| `-x`   | 語呂強引                              | **不可** | — (主観)                             |
| `-r`   | 連想                                  | **不可** | — (主観)                             |
| `-n`   | 馴染みがない                          | **不可** | — (主観)                             |
| `-u`   | 愛称・ユニーク                        | **不可** | — (主観)                             |
| `-m`   | 同数異音混在                          | **可**   | `m`                                  |
| `-s`   | サンド・中抜き                        | **可**   | `!` (中間省略)                       |
| `-p`   | `0xx` (先頭 0 にも読みを割り振ったか) | **可**   | `_` (先頭 0 省略)                    |
| `-a`   | 余りあり                              | 一部可   | 接尾の `n` `-` `.` `..`              |
| `-j`   | 熟語 (真ん中の「ん」「う」の省略)     | 一部可   | 拗音 4 ルール (`encode` の `youon4`) |

### 実データでの付与状況 (2026-08-25)

```
ラベル  手動付与  機械判定  一致
-m         22       243     18
-s         16        20      2
-p          3       201      0
-a        132       367     69
```

**機械判定が手動付与を大きく上回る。** 付け漏れが大量にあるということ。
`-m` は 22 件しか付いていないが、実際に mix なのは 243 件ある。

一方で **`-s` と `-p` は一致がほぼ 0**。同じものを指していない可能性が高い。
「サンド・中抜き」が rankey の `!` (中間省略) と本当に同義か、
「`0xx`」が `_` (先頭 0 省略) と同義かは、**実例を見て確かめる必要がある**。
確かめる前に自動付与すると、意味の違うラベルを大量に撒くことになる。

### scorer との食い違い

`scorer.js` の `LABEL_PENALTIES` は `-x` `-s` `-n` の 3 つだけを
減点対象にしている。**残り 5 種類は付いていても無視される。**

`-m` は `detectMix` で別途 `-0.7` されるので、`-m` ラベル自体は
二重減点を避けるために意図的に外してあるのかもしれない。要確認。

### 機能としての要件 (F)

編集画面でラベルを付け外しできるようにする。

- **主観の 4 つ** (`-x` `-r` `-n` `-u`) はトグルで手入力
- **機械判定できるもの**は「推薦」として提示する。**自動で付けない。**
  意味のズレ (上記 `-s` `-p`) が解消するまでは、人が確認して採用する形にする
- ラベルは語の文字列に埋め込まれている (`ロッシ#enfi -a`) ので、
  付け外しは語の書き換えになる。`PATCH /api/editor/words/{num}` の経路に乗る

## 7. 集約するときの注意

`src/firestore/console-writes.js` が既に部分更新の形を持っている。
これを使う限り、片方の更新が他方を壊さない。

- `saveRep` は `ratings` に触れない
- `saveRating` は `rep` と確定状態に触れない
- `confirmImage` は確定時点の語 (`confirmedFor`) を残す

書き込みは必ず `writeNumber` を通す。`intent` で変更するフィールドを宣言し、
宣言していない保護対象 (`rep` / `ratings`) が変われば拒否される。
