この記事は「000〜999 の数字→単語 変換辞書」を作った過程のうち、**辞書そのものではなく、それを支えた道具立てがどう育っていったか**の話。変換ルールの中身は別記事 [scoring-rules-blog.md](./scoring-rules-blog.md) に書いた。

もしメモリースポーツ上級者の方が読んでくれていたら是非「その道具は〇〇と呼ばれているよ！」とご指摘いただけると幸いです。

# 1. 変遷の整理

最初は「スプレッドシートを 1 枚埋めるだけ」の作業だった。それが、埋まり具合を測りたくなり、スマホで確認したくなり、単語にイメージを添えたくなり……と、欲が出るたびに道具が増えていった。

振り返るとだいたいこの順で育っている。

```
スプシ管理 ──▶ 埋まり度合いの記録 ──▶ アプリ化 ──▶ 画像の取得
                                          │
                                          ├──▶ マップ化（空間で眺める）
                                          └──▶ 99x9 活用 ──▶ 曲作成
```

共通しているのは「**ソースは 1 つ、あとは全部そこから生成する派生物**」という思想。手で触るのは Google Sheet だけにして、アプリ・画像・統計・歌詞はすべて一方向に吐き出す。これを最初に決めたおかげで、道具を何個生やしても破綻しなかった。

以下、道具ごとに順番に。

---

# 2. スプシ管理

## 2-1. 全ての中心は 1 枚のシート

辞書の本体は Google Sheet の 1 タブ（`999`）。1 行 = 1 つの数字（`000`〜`999`）で、人物の語（`hito`）・物/概念の語（`mono`）と、各候補スロットの「単語 / かな読み / 画像」を並べている。

手で編集するのはここだけ、と決めた。ローカルの `words.tsv`、公開用の `data.json`、画像、統計 —— これらは全部このシートから**一方向に生成される派生キャッシュ**。戻す経路はアプリの編集機能ただ 1 本に絞った。

> 🖼️ **図メモ**: 999 タブの実際のスクショ（`num` / `hito` / `mono` / 各スロット列が並んだ様子）。出典: Google Sheet。※新規スクショ要。

## 2-2. sync と push

- `nr sync` … シートを無認証 TSV export で落として `words.tsv` にする（読み取り）
- `nr push` … `words.tsv` をシートに書き戻す（書き込み）

ここに一つ地雷があって、`push` は **タブを clear → 全上書き**する。`words.tsv` に載っていない列（監査フラグ・スコア・4 個目以降のスロット）は sync 時点で読んでいないので、`sync → push` の往復で**消える**。「スコアを書いた直後に push して全部飛ばす」を一度やって、以来 push 前には必ず sync で最新化する運用に固めた。

> 教訓: source of truth を 1 つにする設計は強いが、「往復で欠落する列」を作ると事故る。書き戻すスクリプトが**何を読んでいないか**を常に意識する。

# 3. 埋まり度合いの記録

辞書埋めは長期戦なので、「あと何マス残っているか」が見えないと心が折れる。そこで**埋まり具合を測る道具**をいくつか足した。

## 3-1. 完成度の集計

`nr score` はシートに触らず `words.tsv` だけを見て、埋まっているマス・スコアの合計を出す純ローカル集計。「今日で何個増えた」がすぐ分かる。

## 3-2. かなゴロの分布（`nr stats:goro`）

もう一歩踏み込んで、**「固定した 2 桁を、どんなかなゴロで覆っているか」の分布**を集計するようにした（[goro-stats.md](./goro-stats.md)）。例えば下 2 桁 `22` を覆う語は「ち」が多い、`55` は「た/だ」が多い……というのが見えると、偏りや埋め残しの傾向が掴める。

```
22  (none)=6, ち=3, っ=1
55  た=3, だ=2, (none)=1, ここ=1, の=1, らら=1
```

`(none)` が多いマスが「まだ弱いところ」。ここを狙って埋めると効率が良かった。

> 🖼️ **図メモ**: 埋まり具合は、ルールテーブルを可視化した画面（緑 = 埋まり済のマス）が一目で分かる。→ 既存の [`rules-map.png`](./rules-map.png)（scoring-rules-blog と共用可）。出典: アプリ「その他」タブのルールマップ表示。ゴロ分布（`nr stats:goro`）はテキスト出力なので、上のコードブロックをそのまま図の代わりにしてよい。

## 3-3. check / pt 列と監査

シート側にも記録を残す。各かな列の左隣に監査フラグ `check`、右隣にスコア `pt` を置き、`sheet-audit.mjs` が「読みが数字と噛み合っているか」を採点して書き込む。デフォルトは dry-run で、`--write-pt` を付けたときだけ反映する安全設計にした（前述の push 事故を踏まえて）。

# 4. アプリでの管理

シートは編集には良いが、**思い出す練習**には向かない。電車の中でシートをスクロールするのは辛い。そこで React（Preact）製のアプリを立てて Firebase Hosting に乗せた。

タブごとに用途を分けている。

| タブ         | 用途                                             |
| ------------ | ------------------------------------------------ |
| Number / Digit | 数字グループから語を引く（辞書確認）           |
| Pi           | 円周率を 3 桁ずつ単語化して覚える               |
| Year         | 年号を語呂で覚える                              |
| Card         | トランプ PAO（人・動作・物）                     |
| Bookmark     | 覚えにくいものを退避                            |

さらに全画面オーバーレイの**テストモード**（ランダム出題 → テンキー入力で答え合わせ）と、成績を残す**記録パネル**を足した。「確認する道具」から「鍛える道具」に化けた瞬間。

> 実装メモ: テスト画面は `.test-screen` の全画面オーバーレイで、checking 状態はアプリ全体に持ち上げず画面ローカルに閉じている。

> 🖼️ **図メモ**: 下部タブバー（数字 / カード / π / 年号 / 曜日 / 九九 / その他）が並んだアプリ全体像＋詳細パネルのスクショ。あわせてテストモード（`.test-screen` 全画面 + テンキー）の 1 枚もあると「鍛える道具」感が出る。出典: アプリ本体。※新規スクショ要。

# 5. 画像の取得

単語は文字だけより**絵があると圧倒的に定着する**。`4729 →「しなふく」`と言われてもピンと来ないが、絵が付くと一気に物になる。そこで各数字の語に画像を紐付けるパイプラインを作った。

設計のキモは「**画像バイトは repo に置かない**」。

1. 語で画像検索（DuckDuckGo）
2. webp に変換
3. `sha256(バイト列)` の先頭 20 文字を鍵にして GCS（`anoz-memosupo-words`）へアップロード
4. 公開 URL を `word-images.json` に num をキーにして書き戻す

content-addressed hash なので、**同じ画像は同じ鍵 → 自動 dedup、再実行は冪等**。何度流しても事故らない。詳細契約は [word-images-task.md](./word-images-task.md)。

取得した画像は玉石混交なので、**コンソール（ギャラリー UI）で人力キュレーション**する。良い画像は「keep（ロック）」して、以降のバッチ処理が承認済みを上書きしないようにした。ここは自動化しきらず、最後は目で選ぶ設計にしている。

> 🖼️ **図メモ**: ①コンソールのギャラリー画面（候補画像が並び、keep / ロック状態が色で分かる様子）②アプリ側で数字を選んだとき語＋画像が出る詳細パネル、の 2 枚。出典: 画像コンソール（ギャラリー UI）＋アプリ「数字」タブ。※新規スクショ要。

# 6. マップ化

辞書を「リストで縦に眺める」のではなく、**10×10 の平面に置いて空間で覚える**道具も足した。数字は 2 桁で位置が決まるので、地図のように配置できる。

- **NumMap / YearMap** … 下 2 桁を XY 座標に見立てた 2D マップ。各タイルに候補を置き、面で俯瞰する
- **AllocationGraph** … 「桁 → かな」の割り当てをグラフで可視化（core/sub/bad の色分け、融合の括り）
- **RecallTree（想起ツリー）** … 数字から語を思い出す経路を木構造で表示

リストだと「順番」でしか覚えられないが、マップにすると「あの辺のマス」という**空間記憶**が効く。埋め残しも面で見ると穴が目立つので、[埋まり度合いの記録](#3-埋まり度合いの記録)とも相性が良かった。

> 🖼️ **図メモ**（この章は 3 枚欲しい／全部アプリで可視化済み）:
> 1. 2D マップ（`MapView` / `NumMapTab`・`YearMapTab`）— 下 2 桁を XY に置いたタイル図
> 2. 桁→かな アロケーショングラフ（`AllocationGraph`）— core/sub/bad 色分け・融合の括り
> 3. 想起ツリー（`RecallTreePanel`）— 数字から語への経路の木
>
> 出典: いずれもアプリ（現状は「その他」タブ／テスト機能起動リスト配下）。※新規スクショ要。

# 7. 99x9 活用

辞書が育つと「これ、他の暗記にも流用できるのでは」と欲が出る。その一つが**掛け算の拡張**。九九（9×9）の先、`AB × C = XYZ`（2 桁 × 1 桁）を辞書で読みに変換して覚える試み（`kuku` = 99x9）。

各式を、999 辞書のかな割り当てで 1 本の読みに畳む。

```
reading(AB, C, XYZ) = ab_read(AB) + 'ん' + core[C] + xyz_read(XYZ)
```

例えば `51 × 2 = 102` は `こいん・に・とに` →「**こいんにとに**」。式そのものが呪文のような読みになる。

繰り上がりの有無で難易度を 3 ティアに分けた。

| ティア | 中身                          |
| ------ | ----------------------------- |
| 易     | 足し算なし系 + JI·E0          |
| 中     | JI（両位・足し算あり）        |
| 難     | 足し算が繰り上がる +          |

分類は `A×C` と `B×C` の桁上がりを見て機械的にラベル付けしている（`Ji` 系の記号）。ここまで来ると、辞書は「数字を単語にする表」ではなく「**数字の演算を音に写す変換器**」になっている。

> 🖼️ **図メモ**: 九九タブのリスト表示（`KukuTab` の list ビュー。難易度 易/中/難 の切替、式 → 読みの並び）。出典: アプリ「九九」タブ。※新規スクショ要。

# 8. 曲作成

読みに変換できたら、次は**歌にして流し込む**。バラバラの読みを暗記するより、リズムに乗せた方が続く。

`kuku/readings.csv` の各読みを、**4 読み / 行・全角スペース区切り**でティアごとの歌詞ファイルに並べる（`gen_lyrics.py`）。

```
こいんにとに　こにんにとし　ふぃんことら　こさんにとろ
ふぉんにとぱ　こいんしぶんし　しいんこぶんご　こにんしにんば
りんこみんご　こいんろさんる　はいんこしんご　こいんはしんや
```

意味は無いのに、口ずさむと妙に残る。`51×2=102` を「こいんにとに」と歌えるようになると、逆に歌から式が引ける。辞書 → 演算 → 音 → 歌、と一本の変換パイプで**掛け算表が曲になった**のは、この趣味の中でも一番おかしくて楽しい到達点だった。

> 🖼️ **図メモ**: 九九タブの歌詞表示（`KukuTab` の lyrics ビュー。4 読み/行で並んだ歌詞）。上のコードブロックの実画面版。出典: アプリ「九九」タブ（list ⇄ lyrics 切替）。※新規スクショ要。

# 9. まとめ

道具は全部「辞書を埋める / 使う / 楽しむ」ための派生物で、共通の背骨は変わらない。

> **手で触るソースは 1 つ。あとは全部そこから一方向に生成する。**

この一点を最初に決めたから、スプシ → アプリ → 画像 → マップ → 掛け算 → 歌、とどれだけ枝を伸ばしても元が壊れなかった。辞書作りは 1 年で終わったが、道具作りの方はまだ終わる気配がない。
